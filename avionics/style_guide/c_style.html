Style Guide: C

Overview

C is by far the most common language in use at Sun Devil Rocketry. The Avionics team was founded as a development group for Flight Computers and custom PCBs, all of which have their firmware written in C. In addition, prior to the formation of Avionics as an independent group within the club, they were a subteam of Liquids where a majority of their code was written in C++ (for Arduino), and then C.

As our most common language, we have developed a highly specific code style over time. This was originally formed by our first avionics lead (Colton Acosta) after doing an internship at Garmin, and is heavily inspired by that coding style although there are a few notable differences.

Contact

The authoritative source for style decisions in Sun Devil Rocketry's C code is the project lead for each project, and then the Avionics Firmware lead, which is currently Nicholas Armistead.

SDR Style Guide Golden Rule

All of these rules are general guidance to ensure uniformity and readability in our code. That goal of making our code readable is the most important thing: if you need to violate a rule in order to make your code readable, then please do that instead of conforming blindly to these standards. However, in most scenarios, these rules should work fine.

Indentation/Bracing

We use four spaces per tab for indentation. Ideally, indentation should convert tabs to spaces, but this has never been enforced and we won't be too picky on it as long as your editor displays tabs aligned to the next four spaces.

Arguably the most distinctive feature of our coding style is our bracing. We use a modified variant of Whitesmiths style indentation, which looks like the following:

if ( foo )
{
bar();
}
foobar();

This style places the opening brace on a newline after the condition plus one indentation level. Statements are placed on the same line as the opening and closing brace. After the closing brace, de-indent one level. It is strongly encouraged that you include an extra space after the closing brace as well, although this isn't a hard rule if you have a reason why the next statement should be grouped with the condition.

Conditions

Sun Devil Rocketry has a highly specific style for our conditional statements that are intended to make long predicates easier to digest.

For simple conditions, the important thing to note is the spaces between if/for/while, the opening parentheses, the predicate, and the closing parentheses. For example:

if ( foo )

For compound conditions with two components, it is acceptable to place both on the same line provided the whole condition is visible within the average text editor's width (~60 chars). For example:

if ( foo && bar )

For compound conditions with three or more components, or two components where the conditions are too long to include on one line, our rules get a little bit more complex. An example is provided below:

if ( foo1
&& foo2
&& ( foo3
|| !foo4 )
|| !( foo5
&& foo6 ) )
  1. When conditions span multiple lines, the comparison operator (&&, ||) must line up with the opening parentheses of the previous line or the comparison operator of the prior condition.
  2. When nesting conditions, the whole condition should become indented due to the opening parentheses and extra whitespace per the prior rules. This enables us to group compound conditions in a more digestible way.
  3. The "not" operator is special since it has only one operand and is half the size of the other logical operators. For the "not" operator, place this before a condition, even if it knocks the condition out of alignment with the previous. The exception is when it is outside of parentheses – we would prefer that you align the condition such that rule 1 is preserved.

Conditions: De Morgan's Laws

De Morgan's laws are a set of simple rules in formal logic that state: 

If not(P and Q), then P or Q.

as well as its inverse 

If not(P or Q), then P and Q.

In code, this means:

if !( foo && bar ) ==> if ( foo || bar )

and

if !( foo || bar ) ==> if ( foo && bar )

You can use these rules to simplify complex logical expressions if needed. Be cautious and use your best judgement though – remember that readability is king!

Functions

Function definitions and forward declarations should be written with the return type (and any qualifiers) and the function name on the same line. The opening parentheses should be on the next line indented one level (like our bracing) with the parameters listed one-per-line.

static inline float foo
(
int a,
int b
);

In header files, leave one empty line between function declarations. In source files, leave two empty lines between the last brace of a function and the first line associated with the next function (including comments).

Functions that do not take any parameters are required to be declared with "void" as the parameter.

void foo
(
void
);

Functions: Indentation & Whitespace

Function bracing varies slightly from our usual bracing style: the opening and closing braces should not be indented at all, nor should the contents of the base function block.

void foo
(
void
)
{
int a;
int b;
bar(a, b);
} /* foo */

Note the comment with the function name after the closing brace.

Pointers

This may not seem like it matters, but we have an opinion about where the asterisk should be in a pointer definition. At SDR, pointers are considered their own type, not a modifier of an existing type. As such, we declare our pointers like this:

int* a;

Opinions on this convention differ widely, but we're pretty strongly in this camp. Arguments for alternative conventions can be found in this Stack Overflow post if you're curious. The consensus on our method is that it promotes type safety, which we see as more important than any argument against the convention.

Block Comments

Block Comments are comments at the start of a file or preceding a function. SDR has two conventions for block comments. Doxygen style is our current convention and is required for new files, but there is an old convention you might find in our codebase.

Doxygen

Doxygen is a tool that generates documentation from comments in source code. This guide is written using Doxygen, and it is also used to document a bunch of our projects including our mod library.

In addition to the ability to generate documentation, Doxygen also plays really nicely with VSCode, our preferred text editor. C/C++ intellisense can be augmented to pull from Doxygen comments, which makes writing code easier.

Doxygen: File Comments

The start of a C source file must have some kind of block comment, and under the Doxygen conventions this looks like the below:

/**
  ******************************************************************************
  * @file   debug_sdr.h
  * @brief  Interfaces for debugging SDR embedded firmware.
  ******************************************************************************
  * @copyright
  *
  * Copyright (c) 2026 Sun Devil Rocketry.
  * All rights reserved.
  *
  * This software is licensed under terms that can be found in the LICENSE file
  * in the root directory of this software component.
  * If no LICENSE file comes with this software, it is covered under the   
  * BSD-3-Clause.                                                          
  *                                                                              
  * https://opensource.org/license/bsd-3-clause
  *
  ******************************************************************************
  @verbatim
  ==============================================================================
                      ##### Debug module features #####
  ==============================================================================
  [..]
  (+) Write to a logging interface
  ******************************************************************************
  @endverbatim
  @dir    debug_sdr
  @brief  Provides a unified debug logging interface across SDR embedded code.
          Built for low-memory/no-dynamic-memory/high-reliability environments.
  
  @section dbg_integ Integration Guide
  The debug module is used by a handful of SDR's projects to provide a
  non-blocking debug writer for embedded boards.

  To integrate the module, you need to provide a write callback to debug_init.
  This write callback should meet the following declaration:
  @code
  void overflow_callback_name(const char*, size_t);
  @endcode
  It also needs to call debug_callback_handler after finishing its write. This
  allows for nonblocking operation of the debug module for performance critical
  devices. If your debug writer is blocking, you can safely call 
  debug_callback_handler before returning control flow to the debug module.

  The module also allows you to overwrite the default behavior if the debug
  buffer overflows. As-is, we clear the buffer and queue up a message indicating
  that it overflowed.

  Finally, we include your project's "main.h" header to allow projects to 
  overwrite our default debug buffer size of 2048 bytes. To do this, simply
  define DEBUG_INTF_BUF_SIZE as the number of bytes you want the buffer to be
  in your header.
  *******************************************************************************/

Each line is preceded by a tag. Each of these has a purpose and is formatted in a specific way in the generated documentation.

  1. @file reiterates the file name.
  2. @brief is a short description of what the file does.
  3. @copyright describes the copyright terms of the file. THIS IS MANDATORY AT SDR. Any code that is in an SDR repo is the property of the club. Any exceptions should be cleared with the avionics lead. Our default license is the BSD-3-Clause. Other licenses are acceptable, but we generally prefer permissive licenses over copyleft licenses like the GPL.
  4. @verbatim formats anything between it and @endverbatim as a code block in a monospace font. Some early files that use Doxygen have that tag enclosing normal documentation or extended descriptions.
  5. @dir indicates that the following documentation applies to the directory that holds the file. We recommend that this tag be written in the top-level header of a module.
  6. @section starts a section in documentation. The first argument doesn't really matter, and the second is used as the section name.
  7. @code and @endcode enclose monospaced blocks, usually used for code (duh)

Doxygen: Function Comments

Functions must be documented as follows in both the source and header file: 

/**
  * @brief Add to the debug buffer.
  * 
  * @note Use the macros unless you know what you're doing!
  *
  * @param message A C-string with the message you want to send.
  * @param len The length of the message you want to send.
  * @param log_level The severity of the debug message.
  * 
  * @return The status of the debug module.
  */
DEBUG_STATUS debug_log
    (
    const char* message,
    size_t len,
    DEBUG_LEVEL log_level
    )

Each line is preceded by a tag. Each of these has a purpose and is formatted in a specific way in the generated documentation.

  1. [required] @brief is a short description of the function and its purpose.
  2. @note adds a banner with additional important information to the generated docs.
  3. @warning does the same as the above but with a higher warning level.
  4. @details is a longer description of the function and its purpose.
  5. [required] @param describes a parameter to the function.

The function return MUST be described using one of the following methods:

  1. @return describes what the return of the function represents.
  2. @retval is used for specific return values (i.e. what NAV_BUSY means). You can have multiple @retval tags for the same function.

Also note that the doxygen comment has no space between it and the function definition.

Full Example

/**
  ******************************************************************************
  * @file       debug_sdr.c
  * @brief      Interfaces for debugging SDR embedded firmware.
  ******************************************************************************
  * @copyright
  *
  * Copyright (c) 2026 Sun Devil Rocketry.
  * All rights reserved.
  *
  * This software is licensed under terms that can be found in the LICENSE file
  * in the root directory of this software component.
  * If no LICENSE file comes with this software, it is covered under the   
  * BSD-3-Clause.                                                          
  *                                                                              
  * https://opensource.org/license/bsd-3-clause
  *
  ******************************************************************************
  @verbatim
  ==============================================================================
                      ##### Integration Guide #####
  ==============================================================================
  [..]
  (+) Provide an async debug write callback using debug_init(). If your debug
      write callback is not asynchronous, you risk blocking in the middle of
      a real-time event or otherwise hiding the true performance of the system.
  (+) Ensure you call debug_init() in your initialization sequence before ever 
      logging to it. This can be initialized as soon as the debug write interface 
      is initialized, so consider HAL -> debug write intf -> debug module -> rest
      of init to ensure you get useful logging throughout.
  (+) Register debug_callback_handler (the callback handler) to your async write 
      function's callback handler.
  (+) Optionally, register an overflow handler callback to handle circular buffer
      overflows. This takes the full, constructed message that triggered the 
      overflow as an argument. Pass NULL to use the default handler.
  (+) Do not use the _debug functions directly! Use the macros so that you have
      protection against release builds.
  ******************************************************************************
  @endverbatim
  */

/* Includes ------------------------------------------------------------------*/
#include <stdio.h>

#include "main.h"
#include "debug_sdr.h"

/* Static Variables ----------------------------------------------------------*/
static DEBUG_HANDLE debug_handle; /* This module may be conditionally compiled 
                                     for debug mode only. Holding the handle 
                                     internally helps avoid issues in debug
                                     versus release since we aren't passing
                                     around this giant buffer for no reason. */


/* Private function prototypes -----------------------------------------------*/
static void default_overflow_handler(const char* trigger_msg, size_t len);
static DEBUG_STATUS start_tx(void);

/* Procedures ----------------------------------------------------------------*/

/**
  * @brief Initializes the debug module
  * 
  * @details This function should be called before any other in the
  * debug module, as it initializes pointers and buffers to their
  * correct values.
  *
  * @param write_function Callback to the function that writes over the debug
  *        interface.
  * @param overflow_function Callback to the function that handles the buffer
  *        running out of space.
  * 
  *        Pass (void*)NULL as the overflow callback if you want to use
  *        the default overflow handler.
  * 
  * @return The status of the debug module.
  */
DEBUG_STATUS debug_init
    (
    debug_write_callback write_function, 
    overflow_callback overflow_function
    )
{
/* Begin with an invariant check */
assert_return( write_function, DEBUG_FAIL ); /* exit if nullptr */

/* Initialize the internal debug handle */
memset( &debug_handle, 0, sizeof( DEBUG_HANDLE ) );

/* Set the callbacks */
debug_handle.write_function = write_function; /* already null checked */
if( overflow_function == 0 )
    {
    debug_handle.overflow_function = default_overflow_handler;
    }
else
    {
    debug_handle.overflow_function = overflow_function;
    }

/* Set the circular buffer's pointers */
debug_handle.buf_put_head = debug_handle.tx_buf;
debug_handle.buf_tx_head = debug_handle.tx_buf;
debug_handle.buffer_size_cnt = 0;

/* Clear the transmitting flag */
debug_handle.transmitting = false;

return DEBUG_OK;

} /* debug_init */

/**
 * @brief Reset the circular buffer.
 */
void debug_clear
    (
    void
    )
{
/* Reset the circular buffer's pointers */
debug_handle.buf_put_head = debug_handle.tx_buf;
debug_handle.buf_tx_head = debug_handle.tx_buf;
debug_handle.buffer_size_cnt = 0;
} /* debug_clear */


/**
  * @brief Add to the debug buffer.
  * 
  * @note Use the macros unless you know what you're doing!
  *
  * @param message A C-string with the message you want to send.
  * @param len The length of the message you want to send.
  * @param log_level The severity of the debug message.
  * 
  * @return The status of the debug module.
  */
DEBUG_STATUS debug_log
    (
    const char* message,
    size_t len,
    DEBUG_LEVEL log_level
    )
{
/* Local Variables */
char temp_msg[DEBUG_MSG_MAX_LEN];
size_t true_len = 0;
memset(temp_msg, 0, DEBUG_MSG_MAX_LEN);

/* Begin with an invariant check */
assert_return( message, DEBUG_FAIL ); /* exit if nullptr */
assert_return( len <= DEBUG_MSG_USER_MAX_LEN, DEBUG_FAIL ); /* exit if msg too long */

/* Construct the message to be logged */
switch( log_level )
    {
    case LOG_LVL_INFO:
        true_len += snprintf( (temp_msg+true_len), DEBUG_MSG_MAX_LEN - true_len, "[INFO]: " );
        break;
    case LOG_LVL_WARN:
        true_len += snprintf( (temp_msg+true_len), DEBUG_MSG_MAX_LEN - true_len, "[WARN]: " );
        break;
    case LOG_LVL_ERROR:
        true_len += snprintf( (temp_msg+true_len), DEBUG_MSG_MAX_LEN - true_len, "[ERROR]: " );
        break;
    default:
        return DEBUG_FAIL;
    }
strncpy(temp_msg+true_len, message, len);
true_len += len;
temp_msg[true_len] = '\n';
true_len++;
assert_return( true_len <= DEBUG_MSG_MAX_LEN, DEBUG_FAIL );

/* Check the overflow condition */
if( debug_handle.buffer_size_cnt + true_len > DEBUG_INTF_BUF_SIZE )
    {
    debug_handle.overflow_function( temp_msg, true_len );
    return DEBUG_OVERFLOW;
    }

/* Put the message in the buffer */
size_t space_to_end = debug_handle.tx_buf + DEBUG_INTF_BUF_SIZE - debug_handle.buf_put_head;
if( true_len <= space_to_end )
    {
    memset( debug_handle.buf_put_head, 0, true_len );
    memcpy( debug_handle.buf_put_head, temp_msg, true_len );
    }
else
    {
    /* two copies to handle wraparound */
    memset( debug_handle.buf_put_head, 0, space_to_end );
    memset( debug_handle.tx_buf, 0, true_len - space_to_end );
    memcpy( debug_handle.buf_put_head, temp_msg, space_to_end );
    memcpy( debug_handle.tx_buf, temp_msg + space_to_end, true_len - space_to_end );
    }
debug_handle.buffer_size_cnt += true_len;
/* Gross pointer arithmetic to set the buffer put head */
debug_handle.buf_put_head = debug_handle.tx_buf + ((debug_handle.buf_put_head - debug_handle.tx_buf) + true_len) % DEBUG_INTF_BUF_SIZE;

/* Kick off a transmission if one's not already going */
if( !debug_handle.transmitting )
    {
    return start_tx();
    }
else
    {
    return DEBUG_OK;
    }

} /* debug_log */


/**
 * @brief The function to call after a write completes.
 */
void debug_callback_handler
    (
    void
    )
{
debug_handle.transmitting = false;
if( debug_handle.buffer_size_cnt > 0 )
    {
    start_tx();
    }

} /* debug_callback_handler */


/**
 * @brief Start a transmission over the debug interface.
 * 
 * @return The status of the debug module.
 */
static DEBUG_STATUS start_tx
    (
    void
    )
{
/* Local variables */
size_t msg_len = 0;
uint8_t* tx_addr = debug_handle.buf_tx_head;
size_t space_to_end = debug_handle.tx_buf + DEBUG_INTF_BUF_SIZE - tx_addr;
static uint8_t staging_buf[DEBUG_MSG_MAX_LEN];
memset( staging_buf, 0, DEBUG_MSG_MAX_LEN );

/* Get the length of the string to be written */
for( uint16_t i = 0; i < DEBUG_MSG_MAX_LEN; i++ )
    {
    uint8_t* search_addr = debug_handle.tx_buf + ((tx_addr - debug_handle.tx_buf) + i) % DEBUG_INTF_BUF_SIZE;
    if( (char)*(search_addr) == '\n' )
        {
        msg_len = i + 1;
        break;
        }
    }

/* Check invariants */
assert_return( msg_len != 0, DEBUG_FAIL );
assert_return( msg_len <= DEBUG_MSG_MAX_LEN, DEBUG_FAIL );
assert_return( msg_len <= debug_handle.buffer_size_cnt, DEBUG_FAIL );

/* Kick off write */
if( msg_len <= space_to_end )
    {
    memcpy( staging_buf, tx_addr, msg_len );
    memset( tx_addr, 0, msg_len );
    }
else
    {
    /* Message wraps: write in two halves */
    memcpy( staging_buf, tx_addr, space_to_end );
    memset( tx_addr, 0, space_to_end );
    memcpy( staging_buf + space_to_end, debug_handle.tx_buf, msg_len - space_to_end );
    memset( debug_handle.tx_buf, 0, msg_len - space_to_end );
    }

/* Kick off write */
debug_handle.transmitting = true;
debug_handle.buf_tx_head = debug_handle.tx_buf + ((debug_handle.buf_tx_head - debug_handle.tx_buf) + msg_len) % DEBUG_INTF_BUF_SIZE;
debug_handle.buffer_size_cnt -= msg_len;
debug_handle.write_function( staging_buf, msg_len );

return DEBUG_OK;

} /* start_tx */


/**
 * @brief The default callback for a buffer overflow event.
 * 
 * @param trigger_msg The message that overflowed the buffer.
 * @param len The length of the trigger message.
 */
static void default_overflow_handler
    (
    const char* trigger_msg, 
    size_t len
    )
{
const char* msg = "Debug buffer overflowed!";
/* Clear the buffer and put a new message */
debug_clear();
debug_log(msg, strlen( msg ), LOG_LVL_WARN);

} /* default_overflow_handler */
